# ARI 23 coverage audit and upgrade plan

Audit date: 2026-09-24. Baseline: [Asterisk 23 `rest-api/api-docs` at commit `97d55b3306ca4aa26c0136c67b79470ca4b2b785`](https://github.com/asterisk/asterisk/tree/97d55b3306ca4aa26c0136c67b79470ca4b2b785/rest-api/api-docs). The [endpoint inventory](ari-23-endpoint-inventory.csv) lists all 109 operations in the eleven resource specifications. The [parameter coverage](ari-23-parameter-coverage.csv) classifies all 175 non-path parameters and points to source files for currently mapped options. The [normalized specification manifest](ari-23-spec-manifest.json) records methods, paths, parameter metadata, response classes, and introduction versions from that exact commit.

The status columns measure **route availability**, not full correctness or complete option support. `alternative` means the library reaches an equivalent Asterisk operation through a different documented route; `implemented` still needs option and behavior tests. The five former route alternatives now have explicit methods and wire tests, including optional IDs on collection routes. The proxy event websocket remains represented by a message-bus subscription. This is a source inspection against a pinned specification, not an integration certification against a running Asterisk 23 instance. Asterisk servers on older branches support different subsets of these operations.

Run `go run ./tools/ari-contract` from the proxy checkout to verify that every pinned operation and parameter is classified. To compare a local Asterisk `rest-api/api-docs` directory with the pinned manifest, add `--spec-dir /path/to/api-docs`; changed operations and options fail the check. `go test ./tools/ari-contract` tests drift detection and the wire-test evidence floor. The independent `ARI contract` GitHub Actions workflow runs both commands. Source-file references are evidence of a mapping, not proof of wire correctness. The `ari_wire_test` and `proxy_wire_test` columns now identify evidence for all 175 parameters in the native and proxy paths. These are local wire tests, not proof of behavior against a live Asterisk server.

The Swagger `paramType` is the canonical wire location, but it does not by itself prove that a different encoding is rejected. [Asterisk's channel API specification](https://github.com/asterisk/asterisk/blob/master/rest-api/api-docs/channels.json) says that JSON body fields other than `variables` are interpreted as query parameters for origination. The generated ARI handlers also parse JSON-body fields on many other operations, including [playback control](https://github.com/asterisk/asterisk/blob/master/res/res_ari_playbacks.c). The native client retains JSON bodies for the affected POST/PUT calls. Query-only GET/DELETE calls continue using URL parameters. Verify handler behavior before changing an established request encoding.

## Current route coverage

| Repository | Explicit route | Equivalent route or adapter | Missing operation |
| --- | ---: | ---: | ---: |
| `ari` native client | 109 | 0 | 0 |
| `ari-proxy` client through server | 108 | 1 | 0 |

The proxy's remaining `alternative` is the event websocket, exposed to proxy clients as a message-bus subscription. All pinned REST routes now have explicit native and proxy paths.

The explicit route methods cover bridge creation on `/bridges`, channel origination with an ID in the path, bridge and channel playback on the collection paths, and snooping on the collection path. Asterisk-assigned IDs are read from the response before a handle is returned. The collection methods also accept an optional ID in the JSON body. Proxy calls for these side-effecting routes require an application and target node to avoid fanout to multiple Asterisk servers.

### Event model gap

The event generator now uses the pinned Asterisk 23 `events.json` and the 45 names declared by `Event.subTypes`. It generates the seven previously missing event types (`ApplicationRegistered`, `ApplicationUnregistered`, `CallBroadcast`, `CallClaimed`, `ChannelToneDetected`, `ChannelTransfer`, and `RESTResponse`) and generates referenced payload models separately from the event switch. `ChannelCallerId` remains `ChannelCallerID` in Go for compatibility. Native decoder and proxy round-trip tests cover the seven new types, nested transfer details, and unknown future events. The raw-JSON fallback remains necessary for fields and event types added after the pinned schema. Runtime behavior against live Asterisk 23 is still unverified.

The event copy benchmark exposed a proxy fanout cost proportional to dialog count. On the development machine, the previous 100-dialog decode-and-marshal loop took about 12.5 ms and allocated 2.08 MB per source event. Cloning the top-level event for each dialog reduced the same benchmark to about 3.7 ms and 1.27 MB. These measurements isolate copying and JSON serialization; they do not include message-bus I/O or real subscriber contention. Nested payload values in the clone are shared and must be treated as immutable.

## Implementation sequence

1. **Extend wire-test coverage — complete for the pinned local contract.** The pinned manifest, route and parameter coverage files, local checker, and CI drift check are in place. Native HTTP and proxy client/server wire tests provide evidence for all 175 parameters. They found dropped bridge add-channel options, HTTP status loss on an empty error response, DTMF defaults encoded as zero, unescaped query values, and an empty global variable value dropped by `omitempty`. Existing POST/PUT JSON bodies remain in use where Asterisk parses them. Response fixtures now assert assigned IDs, missing IDs, empty successes, and representative 400/404/409 errors across native and proxy calls, including server-side status propagation. Native errors include the ARI JSON `message` when present. Shared Go fixtures cover selected Asterisk 20/22/23 introduction boundaries; the contract checker verifies them against the pinned manifest, and native/proxy wire tests exercise representative available and unavailable responses. These fixtures simulate versions; they do not certify live servers.
2. **Finish event coverage first.** The generator now iterates `Event.subTypes` from the pinned Asterisk 23 schema, generates 45 typed events and their referenced payload models, and preserves unknown fields and unknown event fallback. Decoder and proxy round-trip tests cover every new type, keyless events, nested extensions, and dialog fanout. A [live Asterisk 22.10.1 check](ari-22-live-validation.md) exercised native and proxy-dispatch calls, an external-media channel, bridge variables, a scoped `BridgeDestroyed`, and a `StasisStart` through native websocket and proxy event serialization. It exposed and fixed fabricated optional event objects. Stored-recording download transferred one bounded proxy chunk. NATS/RabbitMQ delivery and Asterisk 23 behavior remain untested live. Benchmark full message-bus delivery with realistic subscriber contention before further optimization.
3. **Add missing JSON operations to `ari`.** Application event filtering, Asterisk ping, bridge single/bulk variables, channel bulk variables, redirect, progress, transfer progress, RTP statistics, both endpoint REFER routes, and event claim now have native methods and request/response tests. The five route variants with different ID behavior now have explicit methods and request/response wire tests. Continue adding focused HTTP tests for remaining mapped options and error responses.
4. **Carry each operation through the proxy.** Application event filtering, Asterisk ping, bridge variables, the six new channel routes, endpoint REFER, event claim, stored recording download, and both endpoint text-message routes now have proxy payloads, dispatch cases, handlers, and client methods. Proxy REFER and event-claim calls require an application and target node to prevent side-effecting requests from being broadcast to multiple Asterisk servers. Text messages use keyed methods for explicit node selection; the older unkeyed methods select a node only when exactly one live node serves the application. Claim 404/409 status codes now survive the proxy response. Exercise native and proxied clients against the same request/response fixtures.
5. **Add every remaining option.** Asterisk info `only`, bridge create `variables`, add-channel `inhibitConnectedLineUpdates`, playback `announcer_format`, `lang`, `offsetms`, and `skipms`, recording `recorder_format`, channel creation `variables`, playback `lang`, `offsetms`, and `skipms`, external media `transport_data`, hangup `reason_code`, continue `label`, and set-variable `report_events` now have native and proxy forwarding, with focused wire tests. Exercise every mapped parameter and route variant. Keep existing convenience methods as wrappers where possible. Use pointer fields or equivalent presence tracking for optional booleans and numbers, so omitted and explicitly set zero/false stay distinct. Generate parameter test cases from the pinned specification and verify that both native and proxy wires preserve them.
6. **Handle binary recording download deliberately.** `GET /recordings/stored/{recordingName}/file` now returns a streaming `io.ReadCloser` with content type and length in native `ari`. The proxy pulls fixed 32 KiB chunks through short-lived, node-bound sessions instead of putting the whole recording in one JSON response. It caches the last chunk so a retried request does not advance the stream twice, limits open sessions to 64, expires idle sessions after two minutes, and closes the Asterisk body when the client closes the stream. Wire tests cover binary bytes, multi-chunk files, duplicate and out-of-order reads, partial reads, close, and 403/404 errors. Validate cancellation and throughput against live Asterisk and both message-bus backends.
7. **Fix request and proxy behavior discovered during the audit.** Native `ari` now checks HTTP status before decoding a response body, and application unsubscribe and variable reads encode query values. Audit the remaining resource paths and query construction for escaping, and propagate request contexts. The proxy now preserves HTTP status codes for coded errors and logs requests at debug level; continue retaining richer error details where needed and make multi-node list requests report partial failures rather than overwriting the error while collecting replies. Measure latency with the existing 500 ms default request timeout and evaluate it per operation, especially recording and media actions.
8. **Release in major-version order.** Keep the current changes as a coordinated development state. Do not tag `ari/v6` until the selected compatibility contract, endpoint/option tests, event tests, and migration notes pass. Because this proxy checkout now exposes `ari/v6` types through its public API, publish it as `ari-proxy/v6` with its own migration guide, not as another `v5` release. Replace the local `../ari` module override with a real tagged `ari/v6` dependency before publishing or testing a standalone proxy checkout. Keep v5 maintenance fixes on a separate v5 line if needed.

## Completion criteria

Scope decision (2026-10-01): the user accepts existing Asterisk 22.10.1 live
validation for the current release scope. Additional live Asterisk 20/23
validation is deferred and does not block this scope. NATS/RabbitMQ live tests
are deferred for now. The original multi-version goal below remains future
work; retain the pinned contract tests and disclose unverified live behavior.

For each of the 109 operations, the inventory records an explicit implementation or a documented version-gated exception; all non-path parameters have native and proxy wire assertions; JSON response and error cases are tested; binary transfer has bounded memory behavior; event types are either typed or losslessly forwarded; and both libraries pass a common integration suite against selected Asterisk versions. The release gate also checks that a consumer can build each module outside the two-repository sibling layout.
